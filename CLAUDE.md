`constants/profile.ts` reads the `NEXT_PUBLIC_PROFILE_*` and `NEXT_PUBLIC_SOCIAL_*` vars via `req()` / `reqUrl()` helpers that throw at module-load time if any required var is missing — so the build will fail loudly rather than the site rendering with blank names/email/phone. `reqUrl()` additionally rejects strings that aren't valid absolute URLs (e.g. `attakorah.com` without a protocol), guarding against the `new URL()` runtime error in `app/layout.tsx`'s metadata. `NEXT_PUBLIC_PROFILE_MIDDLE_NAME` is the only optional one.

Without the Sheets/email vars, proposal verification and sheet-based posts will silently return empty results — the site still boots, but `/perspective` shows only local MDX, and `/proposal/[id]` will return "not found". Tracker email notifications also no-op if the email vars are missing.

## Architecture

### Content system — local MDX + Google Sheets hybrid (`lib/content.ts`, `lib/google-sheets.ts`)

The `/perspective` blog merges two sources at request time:
- **Local MDX** under `content/perspective/<category-folder>/*.mdx` — category comes from the folder name, mapped via `categoryFolderToName()` (`system-design` → `"System Design"`, etc.)
- **Google Sheets** `BlogPosts` tab — posts with `isPublished=true`, cached 1h via `unstable_cache`

`getPostBySlug()` tries local first, then falls back to Sheets. `getAllPosts()` concatenates both and sorts by `publishedAt`. Read time is recomputed via `reading-time` (200 wpm) in both paths. New categories require adding the folder-name → display-name mapping in `lib/content.ts`.

Frontmatter schema: `title`, `excerpt`, `publishedAt` (ISO), `category` (must match display name exactly), `tags[]`.

### Proposals — gated, Sheets-backed (`lib/google-sheets.ts`, `app/api/proposal/verify/`)

`/proposal/[id]` is a server-rendered dynamic page gated by an access code. The `Proposals` sheet tab stores `id, accessCode, expiryDate, isActive, data` where `data` is a JSON blob matching `types/proposal.ts`. `verifyProposalAccess()` checks active status, expiry, and case-insensitive code match. Access verification goes through `app/api/proposal/verify/` so the access code isn't exposed client-side. `/proposal/*` routes are marked `index: false` in robots and the layout wraps them in `MINIMAL_UI_ROUTES` (see below).

**Offer expiry vs engagement access:** `expiryDate` closes the proposal *offer*, not the engagement. Two checks in `lib/google-sheets.ts`: `verifyProposalAccess()` (strict — rejects past expiry) is used only for submitting an acceptance/counter (`POST /api/proposal/acceptance`). `verifyEngagementAccess()` additionally lets an expired proposal through when its `ProposalAcceptance` status is `accepted`, and is used by the page-level verify route, the acceptance GET, assets, tracker and tracker-approve routes. `isActive = false` revokes everything; malformed expiry dates fail closed on both paths. On an accepted-but-expired proposal the page renders read-only (`isExpired` hides the acceptance form).

**Proposal types and content components:** `ProposalShell` (rendered by the hub's `ProposalTab`) branches on `data.proposalType` to render one of three content shells: (a) the default `ProposalContent` for website projects (e.g. N'Joy Hotel, fixture `GUIDELINES/PROPOSAL01.json`); (b) `ProposalContentChurch` for `proposalType: "church-asset-management"`; (c) `ProposalContentSocial` for `proposalType: "social-media-engagement"` — recurring SMM retainers like Ridge Medical Centre (fixture `GUIDELINES/RIDGE_MEDICAL.json`). The social variant lives in `components/proposals/social/` and adds five new sub-components (content pillars, scope of services, add-ons, engagement terms, cross-sell). It reuses `ProposalHero`, `ProposalOverview`, `ProposalGoals`, `ProposalPricing`, `ProposalRequirements`, `ProposalCTA`, and `ProposalAcceptance` unchanged — only the sections specific to monthly retainers are new. The `ProposalDataUnion` discriminates all three. To add a new proposal type: declare a new `proposalType` literal in `types/proposal.ts`, extend `ProposalDataUnion`, add a branch in `ProposalPageWrapper`, and build the new content component reusing as much of the shared section library as possible.

**Proposal acceptance (`ProposalAcceptance` component):** At the bottom of every proposal page, clients either **accept as presented** or **request changes** (a textarea; stored as `status = "counter"` for compatibility). There is no "accepted with changes" state: a change request leads to a revised proposal, which the client then accepts. Submission goes to `app/api/proposal/acceptance/route.ts`, which writes to the `ProposalAcceptance` sheet tab (columns: `proposalId | status | counterNote | acceptedAt | packageId | paymentPlanId | proposalVersion`). Once a proposal is accepted, subsequent POST attempts are rejected with 409. Change requests can be updated.

**Proposal versions (`lib/proposal-version.ts`):** every response is pinned to the exact terms it was made against. `proposalVersion(data)` is a SHA-256 over key-sorted JSON of `data`, excluding operational keys (`assetsReady`, `trackerReady`, `assets`, `tracker`, legacy `pdfUrl`) so toggling them doesn't count as a term change. `/api/proposal/verify` returns the current version; the page must send it back on submit — a mismatch (proposal edited while the page was open) or a missing version (a page loaded before versioning shipped) returns 409 `stale_version` — the form offers "Reload proposal", which re-fetches in place. Before writing the acceptance row the route stores the canonical JSON once per version in the `ProposalSnapshots` tab (`proposalId | proposalVersion | capturedAt | reason | data`, reason `accepted` or `changes_requested`). `data` is split across consecutive cells E…Z in 49k-character chunks (Sheets' cell limit is 50k); `getProposalSnapshot()` concatenates them back. Beyond E–Z (~1M chars) only the hash is kept and `saveProposalSnapshot` returns `too_large`. Snapshot failures (including `too_large`) are logged and flagged in Joseph's email but never block the client. Client-side display uses `shortVersion()` from `lib/proposal-version-label.ts` (no Node `crypto`). **Revision flow:** while a change request's version equals the current one, the page shows "Changes requested" (with a link to update the request or accept as presented); once Joseph edits `data`, the versions differ, so the form reopens with a "revised since your change request" banner. Rows from before versioning have a blank version and count as "not yet revised". Pricing/plan cards lock only once accepted. **Plans tied to packages:** `ProposalPaymentPlan.packageIds?` limits a plan to those packages (absent = every package; `lib/payment-plans.ts` `planAppliesTo` / `plansFor`). `ProposalContent` shows only the plans for the chosen package (all before a choice; print follows the recorded package), drops an incompatible plan on a package change and auto-selects a lone plan; the acceptance API rejects a mismatched pair (400 `invalid_selection`; a change request just drops the plan); `validateProposal` errors on an unknown id and, when there are plans, on a package no plan applies to (it could never be accepted; shown on the package card); print filters by the *recorded* package only (all plans without one, like the server PDF); the admin plans form has an "Applies to" checkbox list. **Selections are validated against the current version:** the shells only start from a recorded package/plan if that option still exists (they remount per version), the reopened form's summary shows the live selection (the confirmation shows the recorded one), and the API rejects an acceptance whose package/plan isn't in the current proposal (400 `invalid_selection`) — a change request just drops obsolete ids. Every successful POST emails Joseph (`sendProposalResponseNotice` in `lib/email.ts` + `emails/ProposalResponseNotice.tsx`) with the response type (accepted / changes requested / change request updated), the proposal version, chosen package and payment plan names, and the counter note. The send is best-effort — failures are logged and the client's response is still recorded. `ProposalPageWrapper` loads existing acceptance state on mount and passes it as `initialAcceptance` to both content components. The form is hidden (`isExpired = true`) on expired proposals. Sheet setup: a `ProposalAcceptance` tab with headers `proposalId | status | counterNote | acceptedAt | packageId | paymentPlanId | proposalVersion`, and a `ProposalSnapshots` tab with headers `proposalId | proposalVersion | capturedAt | reason | data`.

**Post-acceptance asset collection (`/proposal/[id]/assets`):** The Assets tab opens by itself once the service agreement is executed (or when switched On in the proposal editor) — see "Assets / Progress gates" under Client hub. Enforced server-side: the assets API (GET and POST) returns 404 and the tab shows "not ready" while it's locked. The assets page is gated by the same access code and renders the asset checklist defined in `proposal.assets` (`AssetRequest` type in `types/proposal.ts`). Optional `guideUrl` / `guideLabel` add a second button beside the upload folder for a preparation guide (e.g. IIA Ghana's image-specification PDF; analytics `proposal_asset_guide_opened`). Checklist state syncs to the `ProposalAssets` sheet tab (columns: `proposalId | itemId | checked | checkedAt`) via `app/api/proposal/assets/route.ts`. The Sheets client now uses `spreadsheets` write scope (not `spreadsheets.readonly`). To set up a new proposal's assets: add the `assets` object to the `data` JSON in the sheet, create the `ProposalAssets` tab if it doesn't exist, and grant the service account edit access to the sheet.

**Project tracker (`/proposal/[id]/tracker`):** A live status page for active engagements — vertical timeline of phases and milestones with status pills, completion dates, and short notes from Joseph. Gated by the same access code as the proposal. To enable: set `trackerReady: true` and `tracker: { templates: ["website-project", ...] }` in the proposal `data` JSON. Templates are composable (`constants/tracker-templates.ts` registers `website-project`, `google-business`, `social-media`, and `smm-monthly-engagement` — the last is for recurring SMM retainers, with one onboarding phase plus one phase per contracted month, pre-built for the 3-month minimum); `composeTracker()` flattens them into an ordered phase list. State lives in the `ProjectTracker` sheet tab — columns `proposalId | phaseId | milestoneId | status | startedAt | completedAt | note | updatedAt | notifiedAt`. On first GET the tracker auto-seeds one row per template milestone via `getOrSeedTracker()` (`lib/tracker.ts`); Phase 1's `proposal-accepted` and `service-agreement-signed` are auto-marked `done` from existing acceptance/`assetsReady` state (`proposal-sent`'s `completedAt` is set manually on the sheet since it predates anything the app can observe). The tracker is read-only for the client — Joseph edits the sheet directly to update milestone status/notes.

**Tracker Apps Script (`GUIDELINES/SHEETS_SCRIPT.md`):** A single `onEdit` trigger on the `ProjectTracker` sheet handles both timestamp stamping and email notifications. It fires only on edits to the `status` column (D); the column guard prevents recursion since the script writes to columns E–I. On status changes:

- `pending`/empty → `in_progress`: stamps `startedAt = now` if empty (never overwrites a manual value); clears `completedAt`/`notifiedAt` if rolling back from `done`.
- `pending`/`in_progress` → `done`: stamps `completedAt = now`; also stamps `startedAt = now` if it was empty (covers skipping `in_progress`); POSTs to `/api/proposal/tracker/notify` for the client email.
- `done` → `pending`/`blocked`/`in_progress`: clears `completedAt` and `notifiedAt` (so a future re-completion re-notifies); preserves `startedAt` and `note`.
- `updatedAt` is bumped on every status edit.

**Tracker email notifications:** When the script POSTs to `/api/proposal/tracker/notify` with a shared secret (`TRACKER_WEBHOOK_SECRET`), the route reads the row, sends an email via Resend (`lib/email.ts` + `emails/MilestoneUpdate.tsx`) to `client.email` (optional field on `ProposalClient` — required only for tracker-enabled proposals), and stamps `notifiedAt` so re-edits don't re-spam.

**Apps Script setup (one-time):** Paste the contents of `GUIDELINES/SHEETS_SCRIPT.md` into the sheet's Apps Script editor. Set `TRACKER_WEBHOOK_SECRET` as a Script Property (Apps Script editor → Project Settings → Script Properties), and install the trigger via Triggers → Add Trigger → `onEdit` → from spreadsheet → on edit.

**Weekly update emails (`/api/cron/weekly-update`):** Vercel Cron Job fires every Friday at 18:00 UTC (6:00pm Ghana time — schedule in `vercel.json`). The route is gated by `Authorization: Bearer ${CRON_SECRET}` — Vercel injects this header automatically on scheduled runs; manual hits without the secret return 401. For each proposal with `trackerReady: true` and `client.email` set, the route reads tracker state via `getTrackerStates()`, buckets milestones into Completed-this-week (status=done with `completedAt` in last 7 days), In-progress (status=in_progress), and Coming-up (first 3 pending in source order), then sends `emails/WeeklyUpdate.tsx` via Resend. Skips silently if both Completed and In-progress are empty — a no-news email is worse than no email. Idempotent: a `WeeklyUpdatesSent` sheet tab (`proposalId | weekEndingDate | sentAt`) records each successful send so cron retries don't re-send. An optional `WeeklyNotes` sheet tab (`proposalId | weekEndingDate | note`) lets Joseph attach a free-text note to that week's email — populate the row before Friday; leave it empty to omit the note section.

**Creative brief (`/brief/[id]`):** A gated, server-rendered page for sharing photography mood boards and shot lists with external collaborators (e.g. the project photographer). Distinct access code from the proposal — photographers aren't proposal stakeholders. Schema lives in a `CreativeBrief` sheet tab (`id | accessCode | expiryDate | isActive | data`), same shape as `Proposals`. Verified via `/api/brief/verify` (`app/api/brief/verify/route.ts`). `data` conforms to `CreativeBriefData` in `types/brief.ts`. The gate reuses `components/proposals/ProposalAccessGate.tsx` with `label="brief"`, `verifyUrl="/api/brief/verify"`, `idBodyKey="briefId"`, `responseDataKey="brief"`. Reference fixture: `GUIDELINES/BRIEF_NJOY.json` — copy into the Sheet's `data` column to activate a brief. Sheets layer extracts a private `fetchAccessGatedRows` / `verifyAccessGated` helper that both proposals and briefs reuse.

### Proposal PDF export and print mode (`lib/pdf.ts`, `app/api/proposal/pdf/`, `app/proposal/[id]/print/`)

The proposal CTA offers **Download PDF** (server-generated) and **Print / Save as PDF** (browser dialog). Both render the same components as the live page — never a second template.

- **Print mode:** `ProposalDocumentContext` (`useProposalDocument()`) carries `printMode`, the access code and the *recorded* acceptance. Components use `printMode` only for what CSS can't do: expand collapsed content (`ProposalScope` phases, church cost breakdowns), eager-load images, hide the acceptance form, swap CTA buttons for a static "valid until / accepted on" block, and mark only the recorded package/plan as "Selected" (never an unsaved click). `ProposalShell` holds the `proposalType` → shell branching for both the live page and the print route.
- **Print CSS:** all visual print rules live under `@media print` in `app/globals.css`: A4 `@page`, forced light palette, neutralising framer-motion inline `opacity`/`transform` (ScrollReveal/`whileInView` leave off-screen content invisible), cover page, page-break control via `.print-avoid-break`, and remapping pale dark-theme text shades. The live page enters print mode on `beforeprint` (with `flushSync`), so Ctrl/Cmd+P works too.
- **Server PDF:** `POST /api/proposal/pdf` checks the code with `verifyEngagementAccess`, then `renderProposalPdf()` launches Chromium (`@sparticuz/chromium` on Vercel, `CHROME_EXECUTABLE_PATH` locally), loads `/proposal/[id]/print?token=…` — a server-rendered route authorised by a 2-minute HMAC token from `lib/pdf-token.ts`, 404 without it — waits for fonts/images, and prints at `scale: 0.8` (so two-column layouts apply; `.pdf-document .print-cover` compensates — keep in sync).
- **Cache:** in-memory LRU (20 entries) per function instance, keyed on a hash of proposal data + expiry + acceptance + deployment id; bypassed in development. The printed "Next Steps" block shows the proposal version (and the accepted version if it differs). The old hand-maintained `pdfUrl` field is retired; any left in sheet data is ignored.
- **Versions:** `puppeteer-core` is pinned to the release whose bundled Chrome matches `@sparticuz/chromium`'s major (currently 25.11.0 ↔ 153). Upgrade them together. Both are in `serverExternalPackages`, and `outputFileTracingIncludes` (glob `/api/**/pdf`) ships the Chromium binary with every PDF route — each route is its own Vercel function, so a new PDF route outside that glob would 500 on Vercel while working locally.
- **Theme variant:** `@custom-variant light` is defined in `globals.css`; before it existed, every `light:` utility was silently dropped.

### Admin dashboard (`/admin`, `lib/admin-*.ts`, `app/api/admin/`)

Single-admin surface (roadmap mid-term #1; phases 0, A, B and C shipped — sign-in, dashboard, the proposal editor with structured forms, and publishing revisions with a client email; native agreements (mid-term #3) build on it next, see `GUIDELINES/PLAN_ADMIN.md`).

- **Sign-in (no passwords, no shared code):** `/admin/login` → `POST /api/admin/login/request` emails a 6-digit code via Resend **only to `profile.email`** (never a request-supplied address) and sets an `admin_otp` cookie holding an HMAC of the code + nonce + 10-minute expiry (never the code). `POST /api/admin/login/verify` checks it and sets `admin_session` (HMAC-signed, 12 h, httpOnly, `SameSite=Strict`), then emails a "New admin sign-in" notice. Both cookies are signed with `ADMIN_SESSION_SECRET` (`lib/admin-session.ts`); each token carries a `typ` so one kind can't stand in for the other.
- **Attempts and single use are enforced atomically, server-side:** the `AdminSignIns` sheet tab is an **append-only** event log (`nonce | at | event | ip | userAgent`, event `issued` / `failed` / `matched`). Sheets has no compare-and-swap, so nothing is read-then-updated: each verification appends its own row (`INSERT_ROWS`), Sheets serialises appends, and the request decides from row order alone — it counts only if it's among the first 5 attempts, and a matching code wins only if no earlier attempt matched (`registerAdminSignInAttempt`). This holds across server instances. (A cookie-held counter could be reset by replaying the original cookie; a read-then-write counter races.) It doubles as an audit log. Per-instance throttles (`throttle()` in `lib/admin-auth.ts`) only blunt bursts: one code request per 30 s / 10 per hour, 10 verifications per IP per minute.
- **Two guard layers:** `proxy.ts` redirects `/admin/*` to the login page and returns 401 for `/api/admin/*` without a valid session (login paths excepted), and every admin page/route checks again (`requireAdminPage()` / `isAdminRequest()`). State-changing admin requests also require a same-site `Origin` (`isSameOrigin()`). `/admin` is noindex, disallowed in `robots.ts`, and minimal-UI.
- **Dashboard:** `lib/admin-dashboard.ts` builds one row per proposal from four batched reads (`getAllProposals`, `getAllAcceptances`, `getAllCheckedAssetsByProposal`, `getAllTrackerStatesByProposal`) — reads other than Proposals are settled independently, and a failed one renders as **unavailable** (with a banner) rather than as empty data, e.g. state "unknown" if responses can't be read; a failed Proposals read shows `app/admin/error.tsx` — and derives a lifecycle state: draft (inactive) · sent · expiring (≤ 3 days) · expired · changes requested · revised (change request on an older version) · accepted, plus a "terms changed since acceptance" flag, required-asset and tracker progress. Open change requests (status `counter`) show a two-line snippet in the Response column; clicking it or the state pill expands a detail row (full note, date, the version it was made against, package/plan preference resolved to names, revised-or-not, link to the editor). Below `md` the table is replaced by stacked cards with the same pieces (cards and table use separate `controlsId`s so DOM ids stay unique). The table is the client component `components/admin/DashboardTable.tsx`; shared row types live in `lib/admin-dashboard-types.ts` so it doesn't bundle the Sheets client. Actions: copy client link / access code, admin PDF (`GET /api/admin/proposals/[id]/pdf`, session-gated, shares `proposalPdfResponse()` in `lib/pdf.ts` with the client export), open the proposal, open the sheet.
- **Proposal editor (`/admin/proposals/[id]`, `components/admin/ProposalEditor.tsx`):** Settings panel (active/draft, offer expiry with +7/+30 days, access code with regenerate, client email, assets/tracker unlock — the last three edit the JSON draft directly, so there's one source of truth) plus the full `data` JSON in CodeMirror 6 (`@uiw/react-codemirror`, `@codemirror/lang-json`), with inline syntax and schema diagnostics, an issues list that jumps to the offending node (`components/admin/json-paths.ts` maps `packages[1].totalPrice` to a range via the Lezer tree), Format, ⌘S, and an unsaved-changes guard. A same-origin iframe (`/admin/proposals/[id]/preview`, `ProposalPreview`) renders `ProposalShell` exactly as clients see it (non-interactive), updated by `postMessage` only while the draft is valid; desktop/phone width toggle. CSP `frame-src` includes `'self'` for it. **Structured forms** (`components/admin/forms/`): the Content panel has a Form / JSON switch (default Form, remembered in `localStorage`). Forms cover packages, payment plans (incl. milestone table, blank → `null`, a non-blocking "doesn't add up to 100%" hint) and timeline (`phaseId` is a select of the proposal's tracker phases when `data.tracker` is set) — sections per layout via `layoutOf()` + `LAYOUT_SECTIONS` in `lib/proposal-schema.ts` (default: all three; social: packages + timeline; church: timeline). They are just more `updateData` callers on the same JSON draft, so validation, preview, drafts and saving are shared; CodeMirror stays mounted (hidden) in Form view. Every input has `data-path` (the validation path) so the issues list focuses the field — or switches to JSON for paths with no form field. Cards are disclosure buttons with a `hidden` body (fields stay in the DOM; `REVEAL_CARD_EVENT` expands one) and stay open while they contain errors. Ids are shown behind "Edit id", items the client's recorded response picked are badged, and deleting/renaming them warns. `validateProposal` also rejects duplicate package / payment-plan ids (acceptance resolves selections by id) — only in the sections the layout renders (`LAYOUT_SECTIONS` in `lib/proposal-schema.ts`, shared with the forms), since a section the layout ignores is just an unknown-key warning and must not block saving. Forms only render a section whose values have the right *types* (`formSectionProblem()` in `lib/proposal-schema.ts` — relaxed schemas: missing fields and unknown keys are fine, `packages: [null]` or a numeric `percentage` are not); otherwise that section shows a "fix it in the JSON view" notice linked to the path, and the draft is left untouched. `FormErrorBoundary` wraps the form view as a backstop and resets when the draft text changes. Below `lg` the editor shows one panel at a time (Settings / Content / Preview tabs, Content shows an error-count badge); inactive panels are hidden with `max-lg:hidden`, not unmounted, so CodeMirror state and the preview iframe survive tab switches. From `lg` up it's two columns and the tab bar is hidden. On phones the header collapses to icon-only back/Save (a dot on Save marks unsaved changes).
- **Validation (`lib/proposal-schema.ts`, zod 4):** `z.strictObject` schemas mirror `types/proposal.ts` for the three layouts (selected like `ProposalShell`); compile-time `Equals<z.infer<…>, ProposalData…>` assertions fail `tsc` if a type and its schema drift. Unknown keys are **warnings** (legacy `id`/`pdfUrl`/`validityDays`/`nextSteps` labelled as such), everything else is an **error** that blocks saving — components index into these fields without guards. Also an error: JSON over 49k chars. When real data that renders fine fails validation, fix the *type* (as done for `issuedAt?` and `PaymentMilestone.amount: string | null`), not the schema. All live proposals and `GUIDELINES` fixtures validate.
- **Saving (`PUT /api/admin/proposals/[id]`):** server re-validates; writes `Proposals!A:E` only if the row still hashes to what the editor loaded (`getProposalRowForEdit` / `updateProposalRow` in `lib/google-sheets.ts`) — otherwise 409 `conflict` with the current row, and the editor shows a unified diff with "load sheet version" / "overwrite". Stale-editor conflicts are checked before anything else. The check-and-write runs under `withSheetLock()` — a mutex built on the append-only `SheetLocks` tab (`key | token | at | event`, auto-created): the earliest unreleased `acquire` within its 60 s lease holds the lock, losers release and get 409 `busy` — so two app saves from the same version can't both win (hand edits on the sheet can't take the lock; the hash check catches those). Duplication uses the same lock per new id. **Lease safety:** Sheets can't refuse a write from an expired holder, so holders never *start* a write they can't finish: every write under a lock calls `lock.assertHeld()` first (refuses after 40 s of the 60 s lease, timed from before the acquire — `SheetLockExpiredError` → `busy`, nothing written) and passes `lock.requestOptions` (10 s client timeout). The 20 s margin covers that timeout plus clock skew; the residual risk (a write applied by Google >20 s after it was sent) is documented at `withSheetLock`. **Row anchors:** Proposals and ProposalAcceptance rows are read and written through developer metadata attached to the row (key `andromeda:rowKey`, value = the id in column A; `readRowByAnchor` / `writeRowByAnchor` / `appendAnchoredRow`), never by a row number read earlier — Sheets moves the metadata with the row through hand inserts, deletes and sorts, so those can't redirect a write onto another proposal, and a write to a deleted row updates nothing (save → 404). Anchors are created lazily on a row's first app write (and on append), under the record's lock; each anchored read re-checks column A and rebuilds a stale anchor. A hand edit to the *same* row between check and write is still possible. Tracker/asset rows still use row numbers (roadmap tech-debt item). **Client responses share the lock:** `POST /api/proposal/acceptance` runs its version/selection/already-accepted checks, snapshot and write inside `withProposalLock()` (3 attempts, then 503), and the admin save's accepted-terms check runs inside the same lock via `updateProposalRow`'s `guard` — so an acceptance can't land between the admin's check and write; whichever runs second sees the other (`stale_version` for the client, `confirm_accepted_edit` for the admin). The access code is checked before the lock too, so unauthenticated requests never write lock rows. The accepted-terms check uses the strict `readProposalAcceptance()`; if acceptance can't be read the save is refused (503 `acceptance_unavailable`) rather than skipping the check.
- **Drafts survive navigation:** the "Proposals" link confirms when dirty, `beforeunload` covers reloads/closing, and the draft is kept in `sessionStorage` (per tab, keyed by proposal, with the row hash it started from) so back/forward or in-app navigation can't lose it. Writes are debounced 300 ms while typing; the pending draft is flushed on unmount and `pagehide`, and CodeMirror changes record it synchronously in the change handler (they arrive outside React's event system, so a navigation can unmount the editor before an effect sees the edit). On return it's restored automatically if the row is unchanged, or offered with a warning if the proposal changed since (restoring then meets the normal conflict check). Changing the terms of an accepted proposal returns 409 `confirm_accepted_edit` until resent with `confirmAcceptedEdit` — only when *this save* changes the terms (new version ≠ saved version) and the result isn't the accepted version; operational saves (asset/tracker switches, expiry, access code) never prompt, even after the live terms moved on from the accepted ones. (The switches still live in the proposal JSON as operational keys; moving them to lifecycle state is planned with the client hub, roadmap #2.) Saving a proposal with an open change request publishes a revision (the client page detects the new version).
- **Publish revision (Phase C, `POST /api/admin/proposals/[id]/publish`, `components/admin/PublishRevisionDialog.tsx`):** Save stays the quiet "update the live page" action; **Publish** is the deliberate "tell the client" step. The dialog shows a diff of the draft against the client's change-request snapshot (or the saved row), an optional note (≤ `MAX_REVISION_NOTE_CHARS`), "Email {client.email}" (pre-ticked; address only ever from the saved data) and an offer extension (pre-ticked to today + 14 when ≤ 7 days left, required when expired). The route reuses the PUT validation (`app/api/admin/proposals/[id]/edit.ts`) and, under one `withProposalLock` (via `updateProposalRowLocked`, since taking the lock twice reports `busy`): refuses accepted proposals (409 `accepted`), a version equal to the open change request's (409 `unchanged`), inactive (400) or expired-without-extension (400 `expired_offer`) offers and stale editors (409 `conflict`); saves the row (with the new expiry in the same write); snapshots the version (reason `revision_published`); appends `revision_published` to **`EngagementEvents`** (`proposalId | at | event | proposalVersion | detail JSON | ip | userAgent`, append-only, auto-created). The email (`emails/ProposalRevised.tsx`, `sendProposalRevised`, reply-to Joseph, never the access code) is sent after the lock is released and its outcome appended as `revision_email`; readers fold events per version (`readPublishedRevision` strict / `getPublishedRevision` lenient / `getAllRevisionsByProposal`). Publishing an already-published version records nothing new, but a requested email (`notifyClient`, or the explicit `resendEmail`) is still sent if it hasn't gone out yet (failed, skipped, pending) — never silently dropped, never sent twice. **No duplicate sends:** the decision to send is made under the proposal lock and *reserved* before it's released — the `revision_published` row (notify on) reserves the first attempt; a resend appends `revision_email {status: "sending"}`. Another request that sees a reservation younger than 2 minutes doesn't send (`emailInFlight`, status `pending`); an older one is presumed dead and may be re-reserved. Each send carries a Resend idempotency key `revision-email:{id}:{version}:{recorded failures}`, so a retry after an unrecorded success reuses the key and Resend drops the repeat (a changed payload under a reused key comes back as `DuplicateEmailError` and is recorded as sent, `deduplicated: true`); only a recorded failure gets a fresh key. A retried email states the offer's *current* expiry (this request's, after any extension), not the one recorded with the publication, because expiry isn't part of the terms version. The editor decides "already published" by comparing canonical terms (draft vs saved, plus the saved version being the published one), so expiry, operational toggles and JSON formatting don't make published terms look new. The client verify response carries `revision {publishedAt, note}` only for exactly the current version, rendered by `ProposalRevisionNotice` above the shell (hidden in print and once accepted; `proposal_revision_notice_viewed` analytics). The dashboard's change-request detail says whether a revision is unpublished, published, emailed or failed. Canonical terms JSON lives in the client-safe `lib/proposal-terms.ts` (re-exported by `lib/proposal-version.ts`) so the dialog can diff without Node `crypto`; `components/admin/DiffView.tsx` is shared with the conflict panel.
- **Duplicate (`POST /api/admin/proposals/[id]/duplicate`):** new slug id (3–50 chars), fresh 8-character access code (no ambiguous characters), Draft, 30-day offer, `assetsReady`/`trackerReady` cleared; refuses existing ids.
- **Setup:** set `ADMIN_SESSION_SECRET` (`.env.local` and Vercel). The `AdminSignIns` tab (and `ProposalSnapshots`) is created automatically with its headers on first use by `ensureTab()` in `lib/google-sheets.ts`; the README lists every tab.

### Native agreements (roadmap mid-term #3, `GUIDELINES/PLAN_AGREEMENTS.md`)

The contract is the General Service Agreement + Special Terms (Schedule 1) + the **accepted proposal snapshot** (Schedule 2) — never the live proposal. Joseph signs first (the offer); the client's signature forms the contract (§29.2, §30.1). Status: `draft` → `provider_signed` → `sent` → `executed`.

- **Release gate (`lib/agreement-gate.ts`):** client signing is refused unless the pinned template is `status: final` (it's `draft` until the legal review). `AGREEMENT_CLIENT_SIGNING_ALLOW_DRAFT=1` overrides it only in an allow-listed environment (`VERCEL_ENV` preview/development, or no `VERCEL_ENV` with `NODE_ENV=development`, i.e. local `next dev`); anything else — including `next start` on any host — counts as production. Checked at send, code request, verify, sign and change requests; a sent-but-gated agreement isn't offered to the client at all. Executed agreements stay viewable regardless.
- **Template:** `content/agreements/general-service-agreement-v1.md` (frontmatter `status`; `## N. Title` clauses, `**N.M**` paragraphs; `[[provider.*]]` placeholders; a fenced `drafting-notes` block that's never rendered). `lib/agreement-templates.ts` (server-only) loads it with the **sha256 of the file bytes** (`loadTemplate`), or parses stored text (`parseTemplate`, to render a signed copy); edit terms by adding v2 to the registry, never by changing a signed-against version (signing re-checks → 409 `template_changed`). The registry names each version's client declaration paragraph (v1: `29.3`); `acceptanceDeclaration()` extracts it verbatim for the signing form and the signature record (fails closed if missing). `next.config.ts` `outputFileTracingIncludes` ships `content/agreements/**` with `/admin/proposals/**`, `/api/admin/proposals/**`, `/proposal/**` and `/api/proposal/**`, and the Chromium binary with `/api/**/pdf`, the client sign route and `…/agreement/executed-copy`.
- **Provider identity:** `constants/agreement.ts` (profile name/role/location/email). Joseph is always the contracting party; each agreement may name one of `PROVIDER_ORGANISATIONS` (Avengh, Korah Labs), printed after his role — "Joseph Afriyie Attakorah, Software Engineer, Avengh" — as a description, not a party (`providerAffiliation()`, template placeholder `[[provider.affiliation]]`). The resolved block (incl. `organisation`) is frozen into the record and covered by the hash; no organisation hashes exactly as before. Legacy `contractAs: "trading"` records render as signed ("…, trading as X").
- **Other templates (per-package terms):** a template can be specific to a package. `iiag-platform-licence` v1 (`content/agreements/iiag-platform-licence-v1.md`, `status: final`, declaration `12.3`) is IIA Ghana's Software Licence and Service Agreement for the `pkg-licence` option — signable while the GSA is still gated (the gate is per template). `PACKAGE_TEMPLATES` (`constants/agreement.ts`) maps a package id to its template: the admin panel starts a new agreement on it and warns when the chosen terms don't match the accepted package. `PUT …/agreement` takes `templateId` + `templateVersion` (default: latest GSA). Frontmatter `clientTitle` (default "Service Agreement") is what clients see everywhere — document heading, hub Agreement tab, print title, PDF filename (`proposalPdfFilename(…, clientTitle)`), and the ready/executed emails (`documentTitle`, from `clientTitleOf(record)`); GSA wording is unchanged. Template bodies may use GFM tables (styled in `AgreementDocument`). Each registry entry also names the two sides (`parties`: "Service Provider"/"Client"; the licence "Developer"/"Institute") — signature-block labels, the "Sign as …" button, and the provider's stored declaration (`providerSigningDeclaration()`; GSA wording unchanged). It lives in the registry, not the file, so it never changes a template's hash.
- **Client-facing naming:** clients see "Service Agreement — {project title}" (page, PDF title, `…-service-agreement.pdf`, emails); the base terms' name, version and draft status show only in admin (`AgreementDocument showTemplateInfo`). The client-facing wording lives in **v2** (`general-service-agreement-v2.md`, 2026-10-03: "This Service Agreement" opening, neutral §29.3 lead-in "the person signing confirms that:", `[[provider.affiliation]]`), the default for new agreements; **v1 is byte-identical to what earlier agreements pinned** (hash `7e62963d…`; its `[[provider.tradingAs]]` placeholder is still filled, with the same value). Executed agreements always render from the verified signed copy (admin preview included).
- **Record:** `Agreements` tab (anchored, one row per proposal, A–Q; `sentAt` P, `clientSignature` JSON Q). Missing header cells for appended columns are filled on the next write (`ensureHeaderColumns`); an unknown status makes the row unreadable (never silently a draft). `agreementHash()` (`lib/agreements.ts`) covers template id/version/hash, accepted version, selection, `acceptedAt` (only when present), client name, provider block, special terms and `offerValidUntil` — not the signatures. Offers close at the start of their date, UTC (`offerClosed`).
- **Shared checks (`lib/agreement-basis.ts`):** `loadAgreementBasis` / `loadVerifiedSnapshot` (the accepted snapshot must re-hash to its version, every time — deleted/hand-edited → 409 `snapshot_missing` / `snapshot_mismatch`) and `verifySigningBasis(record, shownHash)` — acceptance still accepted at the same version, selection and date; snapshot verified; client name; template hash; recomputed hash = stored = shown. Both signatures (and sending) run it under `withProposalLock`; `signingFailureResponse()` words the result for admin or client.
- **Admin APIs:** `GET/PUT …/agreement` (draft; `expectedUpdatedAt`; editing a provider-signed or **sent** agreement needs `voidSignature` — a sent one's link is withdrawn, event flag `withdrawnFromClient`; **executed** → 409 `executed`), `POST …/agreement/sign`, `POST …/agreement/send` (`{agreementHash, resend?}`: gate, signed, offer open, re-verified, proposal active, `client.email` from the saved data; writes `sent` + `agreement_sent` (best-effort after the commit — the email goes out regardless), then emails `AgreementReadyEmail` after the lock with idempotency key `agreement-send:{id}:{hash}:{sentAt}:{to}`, outcome `agreement_send_email`; repeating the request while no delivery is recorded for the stored `sentAt` delivers that same send with the same key (outcome `recovered`; Resend drops a repeat), and only a recorded delivery answers `already_sent`; the activity fold shows a send from its email outcome even if `agreement_sent` is missing), `GET …/agreement/pdf`, `POST …/agreement/executed-copy` (admin "Complete follow-up": runs whatever follow-up isn't recorded — onboarding missing or failed, a party without a sent copy, the signing event; `{resend: true}` re-sends both copies). Executed-copy keys are `agreement-executed:{id}:{hash}:{recipient}:{n}` with `n` = that recipient's *recorded failures* (`executedEmailKeySuffix`), so an attempt whose outcome is unknown — lost event, concurrent follow-up — reuses its key and isn't delivered twice; an explicit resend of a delivered copy uses `resend-{recorded outcomes}`. The panel flags "Follow-up incomplete" via `followUpIncomplete()`.
- **Client identity (`lib/agreement-signer.ts`, `lib/signed-token.ts`):** access code → `POST /api/proposal/agreement/code` emails a 6-digit code to `client.email` (throttled per IP / proposal) and sets `agreement_otp` (HMAC of the code + nonce, bound to proposal, agreement hash and the email; 10 min). `POST …/verify` decides via the append-only **`AgreementSignIns`** ledger (`registerSignInAttempt(AGREEMENT_SIGNIN_LEDGER, …)` — same first-5 / single-use rules as admin sign-in, now a generic `SignInLedger`) and sets `agreement_signer` (30 min, bound to proposal + hash + email). Both cookies httpOnly, `SameSite=Strict`, `path=/`. A voided/re-signed agreement has a new hash, so old sessions and codes die. A code only works with the browser that holds its challenge cookie. Both tokens also carry `codeTag`, a keyed fingerprint of the access code entered (`accessCodeTag`, case-insensitive like the gate); every step — verify, the signing page, request changes, sign (inside the lock), session PDF download — re-reads the proposal via `accessStillGranted()` / `authorisedSigner()` and requires it active with the same code, so deactivating a proposal or regenerating its code revokes live sessions (`signed_out`, the form returns to the gate). A network error while signing tells the client the outcome is unknown and to retry (same-signer retries are safe).
- **Client pages:** `/proposal/[id]/agreement` (server): not sent → notice; no session → `AgreementSignInGate`; session → `AgreementDocument` + `ClientSigningForm` (legal name, organisation (prefilled) + role, or individual; the declaration verbatim; "Accept and Sign Agreement"; "Request changes"); executed → `ExecutedAgreementAccess` (PDF behind the access code). The form column is sticky but capped to the window height (it scrolls itself). `/proposal/[id]/agreement/proposal` shows the verified accepted snapshot (Schedule 2 link). `/api/proposal/verify` returns `agreement: {status}` (sent/executed, gate allowing) → `ProposalDocumentContext.agreementStatus` → `ProposalCTA` "Review and Sign Agreement" / "View Signed Agreement".
- **Client sign (`POST /api/proposal/agreement/sign`):** signer session for this hash; under the lock: status `sent`, session = shown = stored hash, provider signature covers it, offer open, `verifySigningBasis`, gate, declaration. Writes the `client_signed` **AgreementSnapshot first** (record with both signatures, terms text, proposal JSON; failure → 503, nothing signed), then `executed` + `ClientSignature` (`legalName, organisation, capacity, email, declarationText, signedAt, agreementHash, ip, userAgent, verification {nonce, verifiedAt}`) — the commit. After the commit nothing fails the request: the `agreement_client_signed` event is best-effort (the follow-up restores a missing one, `restored: true`), and a retry by the **same signer** (session nonce = recorded verification nonce) returns success and resumes the follow-up; any other session gets 409 `already_signed`. Then `after()` runs `completeExecutionFollowUp()` (`lib/agreement-execution.ts`), which does only what isn't recorded yet (safe to repeat; also behind admin "Complete follow-up"), each outcome an event: `unlockOnboarding` sets `assetsReady` (operational key; row-hash write under the lock) and marks the tracker's `service-agreement-signed` done at `signedAt` — adding the row if the tracker was seeded without it (unseeded trackers: `getOrSeedTracker` marks it from the executed agreement; `no_milestone` = the templates don't include it) → `agreement_onboarding_unlocked`; `sendExecutedCopies` renders the PDF once and emails client + Joseph with it attached (without it if rendering fails) → `agreement_executed_email`. `maxDuration = 60`.
- **Change requests:** `POST /api/proposal/agreement/changes` (session) → `agreement_changes_requested` + email to Joseph; the agreement stays `sent`. The admin panel lists them; the dashboard badge says "changes requested".
- **Executed PDF:** `lib/executed-agreement.ts` rebuilds the document from the `client_signed` snapshot only and re-verifies it: `agreementHash` recomputed from the stored record (special terms, provider, selection, dates, client name) must equal the live hash and the hash both signatures cover, and the terms text / proposal must hash to what the record pins (tampered → 404, so no PDF or email). `/proposal/[id]/agreement/print` renders it plus the accepted proposal as an appendix; authorised by a purpose-bound print token (`signPrintToken(id, ttl, "agreement")` — a proposal token can't open it). `renderAgreementPdf` / `agreementPdfResponse` in `lib/pdf.ts`; cache key = hash + both signature times. Client download: `POST /api/proposal/agreement/pdf` (access code, or the signer session right after signing). The live test PDF was 20 pages / 8.2 MB (the appendix carries the proposal's images).
- **Evidence:** `AgreementSnapshots` rows are keyed by hash + signedAt (C), reason `provider_signed` / `client_signed`; the legacy signedAt-in-JSON fallback applies to provider rows only. Voiding re-checks the provider snapshot exists before replacing the record.
- **Activity:** `foldAgreementActivity(events, hash)` (`lib/agreement-activity.ts`) → sends, change requests, executed emails, onboarding for the current hash; used by the admin panel's Client card and the dashboard (one `getAllEngagementEventsByProposal()` read, shared with revisions).
- **Emails:** `emails/Agreement.tsx` (ready-to-sign, signing code, executed, changes requested); senders in `lib/email.ts`. Never the access code; client mail goes only to the saved `client.email`. Links use `NEXT_PUBLIC_SITE_URL`.
- **Admin UI:** `/admin/proposals/[id]/agreement` (`AgreementPanel` + Client card: send/resend, change requests, executed details, PDF, executed-copy status + resend, onboarding; edits locked once executed). Dashboard badge: draft / signed by you / sent to client / changes requested / executed.

### Sheets client and request telemetry (`lib/google-sheets.ts`, `lib/sheets-telemetry.ts`)

- **One client per server instance:** `getGoogleSheetsClient()` builds the client (and its `GoogleAuth`, which caches the access token) once via `createSheetsClient()`; don't construct clients per call. `createSheetsClient({ rootUrl, auth })` overrides exist only for tests against a local stub.
- **Instrumented:** `instrumentSheets()` wraps the client (a proxy over an empty stand-in — googleapis resources are non-configurable properties, so the real object can't be the proxy target) and times every call; calls ≥ 1s, failures (status only, never bodies/credentials/spreadsheet id) and every automatic retry (gaxios `onRetryAttempt`, merged with — not replacing — per-call options like the lock-write timeout) are logged as `[sheets] …`. Retries stay at googleapis defaults (GET/PUT…, 429/5xx, 3 attempts).
- **Per-request summaries:** lock-holding routes are wrapped with `withRouteTelemetry(label, handler)` (AsyncLocalStorage, so concurrent requests never mix counters): `[sheets] agreement sign <id>: 12 calls, 0 retries, <n>ms total, lock held <n>ms`. Wrapped: proposal save, publish revision, client response, agreement save and sign. Request budgets (tested): warm provider sign 12 calls (10 + the snapshot re-verification); +1 on a cold instance (tab check) and +1 for the first Agreements write per instance (header check); +3 when a row anchor must be rebuilt. A live client sign measured 13 calls, ~5.5 s (lock held ~4.2 s).
- **`getProposalSnapshot`** reads the id/version columns, then only the matching row, re-checking the fetched row's id/version (a hand sort between the reads → look again once, then fall back to the full read) — never another proposal's terms.
- **Agreement `clientName`** (column N) is pinned at prepare — and read back **verbatim** (never trimmed: it's part of the agreement hash; Sheets keeps RAW whitespace exactly) — and checked against the verified snapshot at signing; records without it (prepared before the column) take the snapshot's name and get it pinned.

### Client hub (`app/proposal/[id]/(hub)/`, roadmap mid-term #2 — PR A)

The client enters the access code **once**: `POST /api/proposal/session` checks it (`verifyEngagementAccess`) and sets `proposal_session_<hash>` — an HMAC token (`lib/client-session.ts`, `CLIENT_SESSION_SECRET`) holding the proposal id and `codeTag` (keyed fingerprint of the code, `accessCodeTag` in `lib/signed-token.ts`), 12 h, httpOnly, `SameSite=Lax` (so emailed links carry it); `DELETE` signs out. Every use re-checks the proposal through the same `verifyAccessGated` rules with a matcher (`AccessCodeMatcher` in `lib/google-sheets.ts`): active, still that code, past the offer only if accepted — deactivating or regenerating the code ends sessions.

- **Accepted state:** `ProposalCTA` shows "Accepted on {date}" + "What's next" instead of the expiry badge and pitch.
- **Assets / Progress gates (PR B, `lib/engagement-gates.ts`):** one pure rule — a tab is open when its config exists (`data.assets` / `data.tracker`) and its override is `on`, or `auto` (default) and the agreement is **executed**; `off` always locks. When adding fields that should appear in both contexts (e.g. `logos?: string[]`), update **both** files. The `logos` field stores base paths without suffix; `ProjectLogo` appends `_dark.svg` / `_light.svg` at render.

`/writing` and `/writing/*` redirect 308 to `/perspective` and `/perspective/*` respectively (configured in `next.config.ts`). The blog was renamed; some `GUIDELINES/` docs still reference `/writing` but the canonical route is `/perspective`.

## Conventions

### Lint rule gotchas

The ESLint config enables `react-hooks/set-state-in-effect` and `react-hooks/refs`:
- Do **not** call `setState` synchronously at the top of a `useEffect` body. For hydration guards (`setMounted(true)`), wrap in `setTimeout(..., 0)` and clear in cleanup.
- Do **not** read `ref.current` during render. If you need render-time access to a value set in an effect, use `useState` instead of `useRef`.
- The config has no `argsIgnorePattern` — prefixing unused args with `_` does not silence warnings. Remove unused destructured props and map callback args entirely.

### `next/image` with proportional height-constrained SVGs

Use `width={0} height={0}` + `style={{ width: "auto", height: \`${size}px\` }}`. Setting only one of `width`/`height` as a prop while CSS sets the other triggers Next.js's aspect-ratio warning. See `components/projects/ProjectLogo.tsx`.

### `next/image` loading and quality (Next 16)

`priority` is deprecated (it now means `preload`, a `<link>` in `<head>`, which does nothing for images rendered later on the client — the proposal hero renders after the access gate). Use `loading="eager"` for images that must load immediately, plus `fetchPriority="high"` for the LCP image (see `ProposalHero`). Any `quality` other than 75 must be listed in `images.qualities` in `next.config.ts` (currently `[75, 85]`), or Next silently coerces it.

### Three.js resources

`BufferGeometry` and similar GPU resources are not garbage-collected — always `.dispose()` in effect cleanup when the geometry is recreated on dependency change. See `components/sections/hero/HeroBackground.tsx`.
